**Docs/governance only. No implementation.** T4.9 is typed `NO (ruling + measurement)` in

## THE THREE BLOCKED CONSUMERS, PER GOV-2 §2d

`docs/m4-pre-spec-dependencies.md` §2d ("THE LATTICE STRIDE BLOCKS THREE CONSUMERS, NOT ONE — RULE
IT ONCE") named three consumers gated on one architecture call:
1. **Rivers are sub-node features invisible to the traversal lattice** (M4 transport, T4.7).
2. **Village-scale catchments are unrepresentable** (unowned — no milestone has claimed them).
3. **Settlement density is bounded by the stride, not only by the siting rule** (M4 colonization,
   T4.4).

## EVIDENCE

### Current stride

`TraversalLattice.Build(TerrainSet terrain, int stride = 4)` (`Sim.Core/Pathing/TraversalLattice.cs:61`)
— a C# optional-parameter default, never overridden by any production caller
(`SettlementSiting.cs:127`, `CatchmentSystem.cs:94`, `PathBuildSystem.cs:159`,
`Sim.Ui/SimUiGame.cs:222` all call `Build(terrain)` with no stride argument), never exposed as a
`Sim.Data` config/TUNE value. One lattice node aggregates a `stride×stride` = 16-cell raw-terrain
block. At the canonical world (`sizePx=1024`, `kmPerPx=4.0`): 1,048,576 raw cells → 65,536 lattice
nodes, 16×16 km = 256 km² per node.

Two separate per-block aggregation rules (`TraversalLattice.cs:79-87`):
- Movement cost: arithmetic mean over the block.
- Passability: majority vote — `passable[node] = waterSum/cells < 0.5` (impassable only when ≥50%
  of the block's raw cells are water).

### River visibility — STRUCTURALLY INDEPENDENT OF STRIDE, NOT A RESOLUTION ARTIFACT

`Sim.Core/Worldgen/Worldgen.cs:100-148` — direct read of the terrain-generation pipeline:

```csharp
Hydrology.Result rivers = Hydrology.Compute(elevation, water, size, cfg.Rivers);
...
if (water[i] >= 0.5) { fertility[i] = 0.0; continue; }   // land branch handles rivers
...
if (riverDistance[i] <= cfg.Rivers.AdjacencyRadiusPx)
    f *= 1.0 + cfg.Rivers.FertilityBoost;                // river-adjacent LAND gets a bonus
...
return new TerrainSet(size, cfg.KmPerPx, seaLevel,
    elevation, water, temperature, moisture, fertility, movementCost,
    rivers.RiverMask, rivers.Polylines);
```

`water[]` (the array `TraversalLattice`'s passability test aggregates) is computed from elevation
vs. sea level and is a **completely separate array from `rivers.RiverMask`**. River cells are LAND
(`water[i] < 0.5`) that additionally receive a fertility boost near a river channel — rivers are
handled entirely on the land branch of terrain generation, never written into `water[]`.

**Consequence: `TraversalLattice`'s water-majority test never includes river cells, at ANY stride,
including stride 1 (1:1 pixel resolution).** A finer stride would not make rivers "passable water"
via this code path — every stride would see rivers as ordinary land movement-cost cells,
identically. The passability signal simply never reads `TerrainSet.Rivers` /
`Hydrology.Result.RiverMask` at all.

**This corrects the project's own prior shorthand** (`docs/m4-spec.md`, pre-ruling text:
"stride-4 majority-water blocks hide rivers") by one level of precision: the defect is not
resolution-dependent — it is that the lattice's passability signal was never wired to consume the
river mask, independent of block size.

### T3.6b's existing counterfactual — the discriminating measurement, already run

`docs/t3.6b-review-record.md:224-265`, re-read for this ruling (not re-executed — the finding is
architectural and does not require re-running): the lattice-resolution (stride 4) counterfactual
found **0/27** ore-trade-pair crossings even with water made FREE (`r* = 0` for all 27 pairs) — the
lattice pass could see only the sea network. The pixel-resolution counterfactual, built to read
`rivers.RiverMask` directly (a separate code path from the lattice's water field, not a stride
change), found crossings on **4/27** pairs at `r = 0.20`. This is precisely the "give routing a
river-specific representation" fix, already empirically validated — not new speculation, and not
something a stride change would have produced (per the structural finding above, since the lattice
counterfactual's failure held regardless of the stride used).

### Settlement density / colonization (T4.4) — stride is not the bottleneck at M4's scale

`minSpacingKm = 95.2` (ADR-018, ratified) ÷ 16 km/node (stride 4) ≈ **5.95 nodes** between nearest
neighbours — comfortably above the collapse floor `docs/queue.md:52-64` names ("anything below
~32 km would be under two nodes and the isochrone would collapse to a handful of blocks").
Settlement density at M4's actual operating scale is not stride-starved.

### Q4 — the Charter-vs-capacity mismatch remains its own, separate open item

`docs/t4.1-review-record.md:199-209`: Charter target 300–800 settlements (late era) vs. measured
greedy-saturation capacity 33–74 at `minSpacingKm = 480` — a **spacing/map-size** mismatch with
three named closure routes on file (colonization ignoring `minSpacingKm`, changing the spacing
constant, or a larger map, per D-015). **Stride does not appear as a candidate fix for Q4 anywhere
in the record**, and this ruling does not resolve Q4 — it remains KNOWN-DEFERRED SURFACING, exactly
as T4.1 classified it.

### Village-scale catchments — remain unowned, not solved here

No currently-scheduled milestone claims sub-32 km catchments (GOV-2 §2d: "unowned — no milestone
has claimed them"). Per the analytical rule this packet operates under — do not select a finer
stride merely because it would produce more detail, only to fix a KNOWN artifact a real consumer
needs — there is no owning consumer to fix this for yet. This stays open and unclaimed.

### Computational cost of the rejected candidates

`docs/queue.md:62-64` (cited, not re-measured): stride 2 quadruples the node count
(65,536 → 262,144) and the Dijkstra/pathfinding work, plus forces a golden re-pin across every
hash-pinned test. Stride 1 would be 16× the node count (1,048,576 nodes). Neither cost is justified
by any currently-gated M4 consumer, per the evidence above.

### Representation artifacts vs. downstream-consumer defects — the distinction this packet exists to draw

- **Genuine representation artifact** (the lattice geometry itself is the limiting factor):
  village-scale (<32 km) catchments — structurally unrepresentable below ~2 nodes at stride 4.
  Left open, unowned, per above.
- **NOT stride/representation problems, despite being filed under this item:**
  - Rivers — proven independent of stride entirely (structural finding above). A missing
    data-path (lattice → river mask), not a geometry gap.
  - Settlement density/colonization — stride 4 already provides ~6 nodes of separation at
    `minSpacingKm = 95.2`; the actual T4.4 blocker (Q4) is spacing/map-size, already correctly
    filed as its own item.
  - The CR-002 density-corridor denominator bug (`~15×` swing at T3.2b) — a downstream-consumer
    misinterpretation (fertility-weighted node counts read as km² by one consumer, correctly by
    another), already fixed by centralizing conversion in `LatticeGeometry.cs` (ADR-013),
    unrelated to stride's numeric value.

## RULING

**The general lattice stride remains 4 (16×16 km per node). UNCHANGED.**

1. **Do NOT change the stride.** Stride 2 and stride 1 are rejected as unnecessary for every
   currently-gated M4 consumer.
2. **River visibility is NOT a stride-resolution problem.** The lattice's passability signal does
   not consume `TerrainSet.Rivers` / `Hydrology.Result.RiverMask` at any stride — proven
   structurally, not merely observed empirically. The river-routing problem is a downstream
   representation/data-path gap.
3. **T4.7 is responsible for implementing the appropriate river-specific representation**, using
   the existing hydrology river data (`TerrainSet.Rivers`, `Hydrology.Result.Polylines`) — the
   shape T3.6b's pixel-resolution counterfactual already validated. Not implemented here.
4. **T4.4 is unblocked with respect to the lattice-stride dependency.** Its Q4 spacing/map-size
   item remains separately open and is not resolved by this ruling.
5. **Village-scale catchments remain an explicitly open/unowned representation limitation** and
   are NOT to be solved by changing stride — no milestone currently claims them.
6. **Q4's settlement-density / Charter-capacity mismatch remains its own issue**, KNOWN-DEFERRED
   SURFACING per T4.1, NOT solved by T4.9.
