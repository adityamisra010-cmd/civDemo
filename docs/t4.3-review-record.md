# T4.3 — D-037 CLAIM/CONTROL/RECOGNITION DATA MODEL: REVIEW RECORD

**Schema/tables only, per `docs/m4-spec.md:230`. NO polity behaviour, no SimSystem, no pipeline
change.** Cut from `main` `d8d8f48` (the merged, certified T4.2 state).

## THE MECHANISM AS BUILT

Three relation-shaped state tables (`Sim.Core/State/WorldState.cs`), schema v20
(`Sim.Core/Kernel/CanonicalSchema.cs`), all conservation-neutral (no Ledger involvement — not
conserved stocks):

- **`ClaimRow(PolityId Polity, SettlementId Place, double Strength)`** — which polities assert a
  right to a settlement. Multiple rows per place representable (D-037 A3: "MULTIPLE polities may
  hold a claim on the SAME settlement simultaneously").
- **`ControlRow(PolityId Polity, SettlementId Place, double Strength)`** — which polity's orders a
  settlement obeys. **At most one row per place** (D-037 A3: "Exactly one, or none (stateless)").
- **`RecognitionRow(PolityId Recogniser, PolityId Recognised)`** — bilateral, asymmetric; row
  presence alone is the fact, no payload field needed.

New `PolityId` (`Sim.Core/State/Ids.cs`), mirroring the existing `SettlementId`/`GoodId` pattern —
minimal plumbing, no polity registry or lifecycle system.

**All three T4.3 fence prohibitions honored** (`docs/m4-spec.md:232-256`):
- PROHIBITED 1 — no owner-id field on `SettlementRow`.
- PROHIBITED 2 — no boolean/flag field on a polity row.
- PROHIBITED 3 — no stored distance-decay/loyalty scalar; `Strength` is an inert slot a future
  mechanism computes into, not itself a decay formula.

**No polity behaviour implemented.** No system reads or writes `Claims`/`Controls`/`Recognitions`
— the only non-test reference is `PathBuildSystem`'s `NetworkOverlayView` adapter's pass-through
properties, required to satisfy the widened `IReadOnlyWorldState` interface, not logic.

## THE CONTROL-CARDINALITY CORRECTION

The first implementation (`18ba393`) shipped a test asserting two simultaneous `ControlRow`s for
one place were the intended model, reading D-040 C7's "contested where claims overlap" as license
for multiple control rows. **Director audit caught this against D-037 A3** ("CONTROL: ... Exactly
one, or none (stateless)") — D-040 does not amend that cardinality; C7's requirement is about
CLAIM's multiplicity and a later, out-of-scope resolution mechanism, not about CONTROL itself
holding more than one row per place.

**Corrected at `2900e96`:** the multiple-control test replaced with
`Control_IsAtMostOnePolityPerPlace_ExactlyOneOrNone`, proving both valid states (no controller;
exactly one controller). `ControlRow`'s doc comment corrected to match. **No schema/struct change**
— the relation shape already supported the correct cardinality; only the test's claim about it was
wrong. No enforcement mechanism was added, and none is required: no system yet writes `Controls`,
so nothing exists to violate the cardinality. Future control-resolution logic is responsible for
producing the valid zero-or-one state; this packet's job was only to make that state
*representable*, not to enforce it.
