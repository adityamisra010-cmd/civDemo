## 2. ITEM 1 — REAL PER-SECTOR CONTROL

**The mechanism already carried by the tree, restated so the UI design is honest about it:** the
order carries **RAW WEIGHTS**; every consumer reads **NORMALIZED SHARES** through
`Sectors.Share()` (weight ÷ Σweights). The five shares therefore sum to 1.0 *by construction in
the consumer*, not by any constraint on the order.

**How the sum-to-1.0 requirement is enforced, and why.** The packet asks for a stated choice
between "normalise on submit" and "constrain the widget". **Chosen: NEITHER, precisely — the
weights are submitted as typed and the UI DISPLAYS the normalized result that will be applied.**
The reasoning, which is the packet's own third bullet taken to its conclusion:

- Constraining the widget (five sliders that push each other around) makes a five-way
  simultaneous constraint the director has to fight; it is the blunt-instrument failure of the
  farm-% slider in a new costume.
- Normalising on submit *changes the numbers the director typed* before they reach the log, so
  the order log no longer records what was ordered — and the log is replay evidence.
- Submitting raw weights and rendering the normalized shares beside them satisfies the actual
  requirement ("the ORDER carries a valid allocation; the sim never receives a malformed one")
  because **every weight vector with a positive sum is a valid allocation** — validation is
  range-only per weight, and normalization is total. The one malformed case is Σ = 0, which is
  the single guard this packet must add (§3).

So: the director sets five weights; the panel shows the resulting shares as percentages that sum
to 100%; submit emits a five-order batch at the current turn. Normalisation is never invisible
because it is on screen before submit.

**The farm-% slider retires** from the UI. `OrderKind.LaborAllocation` remains in the vocabulary
and in the reader — the fixtures above depend on it — and its legacy mapping (farming = pct,
construction = 100 − pct, others zeroed) is untouched.

**Where the code goes, following the established seam** (the convention is explicit in the tree:
pure model → session method → widget, and `SectorBarModel.cs:9` already reads *"the farm-%
slider and its order path are untouched (controls are T3.9b)"*):

| layer | artifact | mirrors |
| --- | --- | --- |
| pure, headless-testable | `Sim.Ui/ViewModel/SectorOrderFactory.cs` — five weights → five `OrderRecord`s, target packing `settlementId × 8 + sectorId`, plus the normalized-preview shares the panel renders | `ViewModel/LaborOrderFactory.cs` |
| tested seam | `UiSession.EmitSectorOrders(...)` — settlement-existence check then batch `Append` | `UiSession.EmitLaborOrder` |
| draw-only | five `ImGui.SliderInt`s + preview text + submit in `SimUiGame.DrawHud`, emitting on submit | the retiring `farm %` slider |

The preview is computed by the SAME function that encodes the order, so "as it will be applied"
cannot drift from what is sent.

## 3. WHAT THIS PACKET ADDS SIM-SIDE: EXACTLY ONE GUARD, AND ONE FIXTURE PIN

Per the fence, no system is edited. Two test-side additions and one guard:

1. **The Σ = 0 guard.** A five-weight batch that is all zeros normalises to 0/0. `Sectors.Share`
   already returns 0.0 for a zero-sum row rather than NaN, so the sim is safe — but a submitted
   all-zero allocation is a *silently inert order*, the config-fails-quietly class. The UI
   refuses to submit it, and the refusal is proven RED (§7.4).
   **§7.17 note: this is a NEW guard in new code, not a widening of an existing one, so §7.17's
   re-proof obligation does not attach.** If implementation finds itself modifying
   `OrderLog.ValidateRecord` or any existing guard, §7.17 binds in full and every property that
   guard held is re-proven red independently — stated here so the trigger is recognised rather
   than rationalised.
2. **The fixture-vocabulary pin.** The §1 measurement becomes a permanent test: every shipped
   order-log fixture loads at the current `IoVersion` and its records validate. Today it passes
   trivially; its purpose is that a future vocabulary or version change **cannot break the
   M1/M2 regression fixtures silently** — which is exactly the risk the packet's Item 3 was
   written to guard against, relocated to where it actually lives.
3. **The batch-delivery pin (what T3.3's pin does not cover).** T3.3's pin issues five orders for
   five *different* sectors. The UI's batch can also re-issue the *same* sector twice in one turn
   (the director adjusts, then adjusts again before ending the turn) — last-write-wins within the
   batch, in log order. That semantic is unpinned today and this packet pins it turn-exactly.

## 4. PRE-COMMITTED READINGS (§7.13) — EACH WITH ITS §7.15 DISCRIMINATION STATEMENT

§7.15 binds: each reading names its observable, states whether that observable is COMPOSITE, and
where it is, pre-commits the decomposition as part of the reading.

### R1 — WHAT HAPPENS WHEN THE DIRECTOR CAN SET A SANE MIX

**Observable:** Shelter, Comfort and grievance for one settlement, hand-set mix vs the T3.5b
derived default 55/15/10/12/8, on an otherwise identical world.

**COMPOSITE? Shelter: NO — it is now a pure stock read** (dwellings × personsPerDwelling ÷ pop,
T3.8), and the only inputs are the dwelling stock and population. **Comfort: YES, COMPOSITE** —
it is a basket fill over pottery and cloth, moved by (a) the crafting share, (b) the input
materials crafting is capped by, and (c) population as the demand denominator. **Grievance: YES,
COMPOSITE and the worst of the three** — it is a CES aggregate over all three bound needs times
weights, minus decay driven by demographic turnover; it moves when ANY need moves and also when
births+deaths move, with no reference to labor at all.

**Pre-committed decomposition (this is the §7.15 content, not a footnote):**
- Shelter is read directly and needs no decomposition.
- Comfort is decomposed into **pottery fill and cloth fill read SEPARATELY** before any
  interpretation, each as (eaten ÷ demand).
- Grievance is decomposed into **its three per-need satisfaction inputs read separately, plus
  the settlement's turnover (births+deaths ÷ pop)**. A grievance move explained by turnover is
  NOT a labor-mix result and will be reported as a demographic one.

**Expectation, stated in advance.** Against the default, a hand-set mix that raises construction
and extraction should: raise Shelter only if the default was already below 1.0 (T3.8 measured the
canonical world at Shelter 1.0000 at t29 with the store maintaining — so **the pre-committed
expectation is that Shelter does NOT move, because it is saturated**, and a move would mean the
world reached the housing mechanism's unsaturated regime); raise Comfort via the crafting arm;
and lower grievance mainly through Comfort, since Shelter is pinned at its ceiling.

**§7.5 note stated at pre-commitment time:** Shelter at 1.0000 is a quantity resting against its
own limit. A reading that asserts "Shelter improved" cannot fire there. That is why Comfort and
the turnover arm carry the discriminating load in R1, and why R1's headline claim is about
Comfort rather than Shelter.

- **Matches** → report and proceed.
- **Diverges** → report which term moved and by how much, decomposed as above. The default is
  NOT adjusted (T3.5b derived value; CR-003 §5.1 governs).

### R2 — THE TRADE PANEL ON THE CANONICAL WORLD

**Observable:** the count of `TradeFlows` rows on the canonical world after the panel's own
horizon, and what the panel renders for that state.

**COMPOSITE? NO — a row count is atomic.** But the *reading* built on it would be composite if
stated as "the panel is correct", because an empty panel is produced both by "no trade occurred"
and by "the panel is broken". **Pre-committed discrimination:** the panel's correctness is
established on the RIG (§5), which produces nonzero flow; the canonical world establishes only
the zero-flow reading. The two are asserted by different tests and neither is allowed to stand
in for the other. This is §7.5 applied exactly as the packet instructs — a display test whose
only subject is a zero-flow world asserts against a limit.

**Expectation, stated in advance:** zero flow, and the panel says so legibly with the reason
surfaced from data already present (per-good gap vs deadband).

- **Zero, panel legible** → discharged.
- **NONZERO** → STOP. Something changed in trade since T3.6 and that is larger than this packet.

## 5. ITEM 2(b) — THE RIG, CONSTRUCTION STATED

The canonical world cannot exercise a moving trade panel (T3.6: zero flow; 11 of 13 non-grain
goods gap-zero on common band edges; the one divergent good faces a deadband above its maximum
possible gap). Following the T3.4c land-cap and T3.4d near/far precedents, the display is
asserted against a **constructed** two-settlement world, not a sampled one:

- Two settlements, hand-built, with an **asymmetric good endowment** — one holds a large stock of
  a tradable good, the other holds none — so the price solver produces a gap that is not
  identically zero and not at a shared band edge.
- The pair's path cost is set so that `deadband = bulk × pathCost × 0.16` is **strictly below**
  the resulting gap. The rig states its computed deadband and gap and **asserts the margin
  between them**, so the rig cannot go vacuous silently (T3.4d's asymmetric-margin lesson;
  §7.16 binds on the margin statement — the thin side is named at the moment the numbers are
  chosen).
- The rig asserts the PANEL's rendered content against the flows the sim actually produced, not
  against hand-written expectations.

## 6. FENCE

No sim mechanism change (no system edited). No trade mechanism change — display only. No store
bounding, no transport, no merchants, no housing tiers. No band edge moved. `IoVersion` stays 1.
`OrderKind.LaborAllocation` stays in the vocabulary and reader.

**Goldens:** an added order TYPE would not move a world golden if no order is issued — and this
packet adds no order type at all, issues no order in any golden path, and edits no system. The
pre-committed expectation is therefore **that no golden moves**. If any moves, the cause is
stated exactly before any re-pin, and the re-pin happens at most once, itemized.
