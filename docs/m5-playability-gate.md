# M5 PLAYABILITY GATE (M5 hardening, stream H1)

**Status:** the standing playability gate for every playable build from M5 on (Director 2026-10-05 §15: a build is
not "playable" because the test suites pass; it must also pass the manual-interaction-equivalent smoke gate).
Created 2026-10-05 on branch `m5h-h1-ui-playability` (cut from `9bb7423`). This record describes what the gate
does and what it found; the coverage table in §6 is generated by the gate itself (`Sim.Ui --smoke --report`).

Labels as in `docs/m5-playtest-baseline.md`: **MEASURED** (run by the author of this record on this branch),
**IMPLEMENTED** (read in the tree), **INFERRED** (reasoning, not measured).

---

## 1. Why this exists

The playtest build of 2026-10-04 passed Sim.Tests 1460/0/6 and Sim.Ui.Tests 473/473 and aborted on the first click
of Research:

```
imgui_draw.cpp:2261  ImGui::AddDrawListToDrawDataEx
Assertion: draw_list->_VtxCurrentIdx < (1 << 16) && "Too many vertices in ImDrawList using 16-bit indices."
```

None of the 473 UI tests created an ImGui frame. The UI's view models and DrawList painters were tested; the live
path — the ImGui widgets, the DrawList replayed into ImGui's draw lists, `ImGui.Render`, the input routing between
MonoGame and ImGui — was never run outside a window. This gate runs exactly that path.

## 2. The Research-screen crash

**Reproduced (MEASURED).** The canonical founded world (seed 42) at turn 1, the Research screen painted by the
real `ProgressionScreen`, replayed by the real `DrawListImGuiBackend` into a real native ImGui context (ImGui.NET
1.91.6.1's `cimgui`), then `ImGui.Render()`. Without the fix the process aborts with the exact assertion above
(`imgui_draw.cpp:2261`); `Sim.Ui --smoke-control-prefix` reproduces it through the live UI on demand.

> **DATED NOTE 2026-10-06 (M5 polish, UI readability UR-2).** The calmer card texture (texture in the frame band,
> one mark in four and faint over the words) brought the A1 tree at the default 1280×800 window under 65,535 vertices
> (at most 62,618 while hovering, measured). The control and its regression test
> (`PlayabilityGateTests.ResearchClick_ThroughTheLiveUi_MaximisedWindow_…`) therefore open the maximised 1920×1080
> window the Director's crash was in, where the A1 tree is ≈ 96,000 vertices as it opens; the fix (the declared
> `RendererHasVtxOffset`) is unchanged and still required there. The figures in the tables below are the H1
> measurements, kept as recorded.

> **DATED NOTE 2026-10-06 (M5 polish UR-4/UR-7).** The Research screen's cards grew (Body-role names on two lines,
> ~208–232 × 116 px) and the type with them; the 16-bit regression still renders the A1 tree past 65,535 vertices
> (asserted by its control) and is extended to 2560 × 1440 at UI scale 1.375 and 3840 × 2160 at UI scale 2
> (`ReadabilityStageBTests.TheResearchScreen_AtTheLargeWindowsAndTheirScale_…`, every frame inside the draw-data
> contract). In a window narrower than 1600 px a selected node's detail is an overlay drawer: the gate's research
> checks skip cards under it (`ProgressionScreen.Obscured`) and its Escape check closes the drawer, then the screen.
> The game now opens at 90 % of the display (`PanelLayout.OpeningWindow`); the gate's windows are unchanged.

**Root cause (IMPLEMENTED, MEASURED).** ImGui indexes vertices with 16-bit indices. A draw list may pass 65,535
vertices only if the renderer declares `ImGuiBackendFlags.RendererHasVtxOffset`; ImGui then opens a new draw
command whose `VtxOffset` rebases the indices, and the renderer adds that offset to each command's base vertex.
The vendored MonoGame renderer (`Sim.Ui/ImGuiIntegration/ImGuiRenderer.cs`) already passed
`baseVertex = vtxOffset + cmd.VtxOffset`, but **nothing ever set the flag**, so every draw list stayed in one
16-bit window. The Research screen is replayed into ONE draw list (ImGui's background list). In the A1 (stone)
era every card carries a pitted-stone texture and freehand outlines, so the A1 Technology tree is large:

| window | A1 Technology tree | vertices in the one draw list (MEASURED) |
|---|---|---|
| 1280×800 (the game's default window) | as it opens | 60,310 |
| 1280×800 | pointer moved over the tree (hover highlight) | up to 68,034 |
| 1280×800 | FIT (whole tree) | 88,362 |
| 1920×1009 (a maximised window) | as it opens | 94,664 |
| 2560×1377 | as it opens | 130,088 |

So in a maximised window the screen crossed 65,535 on the very frame it opened, and in the default window as soon
as the pointer crossed the tree or FIT was pressed. A5/A9 trees stay far below (19,034 / 16,952 at 1280×800).

**Fix (IMPLEMENTED).**
- `ImGuiDrawData.Configure` sets `RendererHasVtxOffset` (called by the renderer's constructor and by the headless
  context) and keeps ImGui's duplicate-ID detector on.
- `ImGuiDrawData.Plan` is the one place a draw call's base vertex (`list start + cmd.VtxOffset`) and start index
  (`list start + cmd.IdxOffset`) are computed; the renderer issues exactly that plan.
- `ImGuiDrawData.Check` validates a rendered frame against the REAL index buffers: the flag is declared, every
  command's indices stay inside its list's index buffer, every index rebased by its `VtxOffset` addresses a vertex
  of the same list, and every list's open 16-bit window is below 65,536.
- `DrawListCull` drops DrawList commands whose conservative bounds miss the target's clip rect (the screen for the
  background list; a window's visible region for a window list), honouring the list's own clip pushes, before
  replay. Its bounds are proven to contain every vertex ImGui emits for each command kind.

The assertion is not suppressed and the screen is not disabled.

**Regression tests (`Sim.Ui.Tests/ResearchScreenRenderTests.cs`, real native ImGui, headless).** Technology and
Civics at A1, A5 and A9, each scrolled from top to bottom at zoom 1, fitted, zoomed fully out and hovered: every
frame passes `Check`. Control: the A1 Technology tree exceeds 65,535 vertices in one list (and opens past it at
1920×1009), and ImGui split it into rebased commands. The draw plan is pinned command by command against the real
index buffers. The cull's bounds contain every emitted vertex per command kind; every command it drops is
replayed alone and shown unable to reach the visible region. Mutants each killed by a semantic test: no flag; plan
without `VtxOffset`; text bound shrunk to 0.4 em per character; clip pushes ignored.

## 3. The gate

**Architecture (IMPLEMENTED).**

| piece | file | role |
|---|---|---|
| `GameUi` | `Sim.Ui/GameUi.cs` | The game's per-frame UI WITHOUT a graphics device: chrome, sections, research and Age screens, action surface, world lens, map interaction, keys. Moved verbatim out of `SimUiGame`. |
| `SimUiGame` | `Sim.Ui/SimUiGame.cs` | A thin MonoGame host: polls input once per Update, draws the terrain bake, rivers and grain on the GPU, calls `GameUi.Update` / `PrepareFrame` / `Draw` between the renderer's BeforeLayout and AfterLayout. |
| `UiControls` | `Sim.Ui/UiControls.cs` | Every ImGui widget records its name, rect and item id each frame. The gate clicks controls where the UI drew them; a repeated item id is a duplicate-ID defect. |
| `ImGuiInput` | `Sim.Ui/ImGuiIntegration/ImGuiInput.cs` | The one MouseState/KeyboardState → ImGui IO translation, used by the renderer and the harness alike. |
| `HeadlessImGui` | `Sim.Ui/Headless/HeadlessImGui.cs` | A real native ImGui context, font atlas built on the CPU, stand-in texture ids, no GPU. |
| `UiFrameHarness` | `Sim.Ui/Headless/UiFrameHarness.cs` | One MonoGame tick per `Frame()`: `GameUi.Update` with scripted input, `ImGui.NewFrame`, `GameUi.Draw`, `ImGui.Render`, then the frame checks (16-bit draw contract, duplicate ids, ImGui's error tooltip). Click = move and hold 3 frames, press, release, one frame for the result. |
| `PlayabilityGate` | `Sim.Ui/Headless/PlayabilityGate.cs` | The states, the per-control script with its expected transitions, and the seeded monkey. |
| `SmokeCommand` | `Sim.Ui/Headless/SmokeCommand.cs` | `Sim.Ui --smoke`: runs the gate, prints the table, exits 0 / 1; routes Windows C-runtime assert dialogs to stderr; a watchdog makes a hang a failure (exit 3). |

**Commands.**

```
Sim.Ui --smoke [--ai-empires N] [--monkey N] [--state NAME]... [--report PATH] [--timeout-minutes M]
Sim.Ui --smoke-control-prefix      # the control: the live UI without RendererHasVtxOffset; must abort
Sim.Ui --frame-cost [--rounds N]   # the Research-screen frame cost table of §2
```

`--ai-empires N` founds every state with N AI empires (by default the states are founded with none, plus one
state with one AI).

**What a check is.** For every interactive control the code draws: click it where it is drawn → no crash → assert
the intended transition (a section opens, a toggle flips, a draft changes, an order is appended to the session's
log, the selection changes, the turn advances, the Age advances, the camera moves …). A control that is not
available in a state must be ABSENT with a stated reason, or visibly locked (a locked research node selects and
its detail panel's button reads LOCKED / KNOWN / CURRENT RESEARCH TARGET / ORDERED; CONFIRM ADVANCE is dim until a
surge is chosen and says so). A control that is drawn but does nothing is a FAIL ("SILENT").

**Every frame** of every check and of the monkey is checked: the draw data's 16-bit contract
(`ImGuiDrawData.Check`), duplicate ImGui item ids among the recorded controls (exhaustive), and ImGui 1.91's own
duplicate-ID warning (`io.ConfigDebugHighlightIdConflicts` is on; its error tooltip window `##Tooltip_Error` is
detected in the draw data — the game draws no tooltips). Both detectors are proven to fire on an injected
duplicate (`PlayabilityGateTests.DuplicateImGuiIds_AreReportedByBothDetectors`).

**The monkey.** A seeded SplitMix64 stream (seed 20261005) chooses, per action: left click (50 %), right click,
drag, wheel ±3, or a key tap from K, Escape, Tab, 1–7, F12, W/A/S/D, arrows, Space (End Turn, at most six per
state), Enter. 400 actions per state by default; an Escape with nothing open is acknowledged (it would exit).

**Out of process.** A native ImGui assertion aborts the process, so the tests run the full gate as a SEPARATE
process (`dotnet Sim.Ui.dll --smoke`) and assert exit 0 and "SMOKE PASSED"; the A1 state and focused scenarios also
run in-process where safe (the capability is declared, so a large list cannot abort).

**Windows.** `.github/workflows/ui-artifact.yml` job `windows-smoke` (windows-latest) downloads the exact win-x64 zip
the `ui-artifact` job published and runs its `app/Sim.Ui.exe --smoke` (the zip's own `cimgui.dll`), failing the
job on a non-zero exit or a missing "SMOKE PASSED"; an informational step runs the control, which must abort. See §8.

### 3.1 The info area (M5 polish, stream INFO, 2026-10-06)

Shift+left click is the universal "what is this?" gesture (directive §9). The gate has an **info** area that runs in
every state (`Sim.Ui/Headless/PlayabilityGate.Info.cs`). Each surface records the subjects it paints in
`GameUi.InfoRegistry` as `InfoQuery` subjects, each at the rect where it was drawn. The gate Shift+clicks one subject
of every kind that surface paints:

| surface | kinds Shift+clicked |
|---|---|
| POLICY (scrolled into view) | labour activity, good, Learning, research node, Age, project, craft (recipe), road class, tax edict, formation, standing capability, university type |
| Age panel | Age milestone, Age, the "research next" node; plus "Show in research tree" from a milestone's card (the tree opens with that node selected) |
| status band | the research chip and the Age chip (the card opens and the screen does not) |
| map | the player's formation token (the selection does not change) |
| research tree | an AVAILABLE card (no research target is ordered), an "opens the way to" entity in the detail panel, an INSTITUTIONS-lens item |
| player views | a Work line (Place), the tax line (Empire), a founded institution (Institutions) |
| hover hint | "Shift+click: details" is painted beside the pointer, and no ImGui tooltip window exists |

A row **passes** only when all of the following hold:
- The card opened for exactly that subject, with the title `InfoQuery.Card` gives it and a non-empty status line.
- **No order was queued** and the **world hash is unchanged**: Shift+click never acts.
- Escape then closed the card first, with no exit request, and the surface underneath was still open.

A kind that a surface does not paint in a state is "not offered", with the reason. A Shift+click that opens nothing
is a FAIL. Before picking a region, a check waits a few frames after a view opens. ImGui sizes the scrolled body
from the previous frame's content, so the body's scrollbars appear one frame after the view opens. A line that was
visible in the opening frame can then sit under a scrollbar. The checks also pick a region that is clear of the
panel's bottom edge by more than a scrollbar's width, and scroll it into view first, as a player would. In-process
tests for the same behaviour are in `Sim.Ui.Tests/InfoPanelTests.cs`.

The §6 tables below were generated before this area existed and were not regenerated. The full run on this
branch's final commit is in the stream report.

no simulation, serialization or order code changed.

**What the frame says (IMPLEMENTED).**

| piece | file | what it is |
|---|---|---|

**FrameText is complete — two independent proofs (`Sim.Ui.Tests/FrameTextTests.cs`).**
- *Source guard.* No ImGui call in Sim.Ui that can draw text or submit a widget sits outside an allowlisted file,
  and each allowlisted file holds exactly its stated count. The calls covered are text, labels, buttons, checkboxes,
  radios, selectables, trees, tabs, menus, combos, sliders, inputs, plots, tooltips, `Begin`, any draw list's
  `AddText`, and any `ImGuiNative.ig*`. The allowlist has 10 entries, each with its reason: the 9 helpers, and the
  backend's 3 `AddText` calls in its `TextCmd` replay. An alias of ImGui (`using static`, `using X =`) is itself a
  violation. Ten bypass shapes are mutants of the real tree, and each is reported at its line: a direct call, a
  fully-qualified call, `dl.AddText`, `TextWrapped`, `SetTooltip`, a native call, a call after a string holding `//`,
  an extra call in an allowlisted file, and both alias forms. A call written inside a comment is not reported.
- *The replay channel (review fix).* Most of the game's text is `TextCmd`s that the DrawList backend replays, and only
  GameUi's `Backend` reports them. Neither proof above saw that channel. ImGui's text log never sees draw-list text,
  and the guard counted only the backend's own `AddText`. A surface replayed through a fresh
  `new DrawListImGuiBackend(_fonts)` (the idiom at about 10 GameUi sites before P6) put its text on screen with no
  FrameText entry, and every P6 test stayed green. The reviewer measured this at 4 sites, and 30/30 tests passed. The
  guard now pins the channel too, with a count-pinned allowlist of 6 entries, each with its reason:
  - the backend's type may be constructed only in `GameUi.Text.cs` (with the sink) and in `FrameCost.cs` (the
    `--frame-cost` measurement, which draws its own bare frame);
  - the type may be named in any other way (a declaration, parameter, cast or alias) only at those sites and in the
    class itself;
  - GameUi's backend field may be named only in `GameUi.Text.cs`;
  - every `.Render(` in GameUi's files must be `Backend.Render(`.

  *Integration note (2026-10-10, m5w-integration).* P4's `--frame-cost map` (`Sim.Ui/Headless/MapFrameCost.cs`)
  was written on a branch parallel to this guard. When the two branches merged, the guard reported its five namings of
  the backend type (20 of 34 FrameTextTests red). It is the same kind of site as `FrameCost.cs`: a headless measurement
  that replays `WorldLens.Paint` into bare `HeadlessImGui` frames of its own, with no GameUi and no FrameText. So it
  gets two count-pinned entries of its own (2 constructions, 3 parameter namings), each with its reason. The allowlist
  now has 8 replay-channel entries. No entry was widened and no mutant row changed.

  Nine more mutants of the real tree are reported: the measured mutant's four sites, a `.Render(` on another receiver,
  a second backend held in a target-typed field, the field rebound to a new backend, a construction elsewhere in
  Sim.Ui, and a second construction in the helpers' file. The sink is init-only, so `Backend.Replayed = null` does not
  compile (`ReplaySink_IsInitOnly`).
- *Every replay site, semantically.* `EveryReplaySite_RecordsItsSurfacesOwnText_AsReplayed` opens each surface the
  game replays and requires the text its own model says it shows, under its surface, as `Replayed`:
  - the lens (one of `LastLensCommands`' texts);
  - the status band's styled runs;
  - the selection card's title row;
  - the Age panel (the capital's name, and `AgePanelModel.CurrentAgeName`), with nothing under the Age surface while
    the panel is closed;
  - every labour activity of the POLICY action surface's model;
  - the hover hint (`InfoPanel.HintText`, while `InfoHint` says it shows);
  - the pinned info card's `InfoCard.Title`;
  - the formation card's title;
  - every word of the research screen's focused node.

  The notices toast is pinned by its own test. The panel furniture's replay has no text.
- *ImGui's own text log.* ImGui writes everything it renders as text to a file (`LogToFile`) for one frame. Every
  string it wrote must be one FrameText recorded, leaving only ImGui's own log furniture: button brackets, checkbox
  and radio markers, separator dashes. This is checked on every surface after a played turn: the map, every section,
  POLICY with its record open and scrolled, TRENDS in both scopes and the price metric, every developer tab and
  settlement tab, the grievance factors, the formation card, the Age panel, a pinned info card, and the research
  screen. The mutant is one direct `ImGui.TextUnformatted` and one `ImGui.Button` added to a real frame. ImGui
  renders both, FrameText never hears of them, and the check names both. The same frame without them leaves nothing.

Also pinned there:
- FrameText names the selected settlement on the selection card and follows the selection.
- In a world with no settlement (the only way nothing is selected), no surface draws any settlement name. The same
  search finds the name in the canonical frame (the control).
- Every lens string replayed is among `LastLensCommands`' `TextCmd`s, in paint order.
- *The recorders only observe.* A live UI that drew and recorded every section, the developer surfaces and the
  research screen, then ended the turn through its button, holds exactly the bare session's world, hash for hash,
  before and after the End Turn.

**Gate control coverage (IMPLEMENTED, `Sim.Ui/Headless/UiCoverage.cs`).** Every control and screen region a player
can act on has a coverage key:
- `control:<family>`: a recorded ImGui widget. A run of digits reads `#`, and the TURN audit lines are one family,
  `audit-*`.
- `hit:<surface>.<kind>`: a hit region of a screen that is showing (research, age, policy, card).
- `info:<kind>`: an inspectable region.

The harness collects every key drawn in any frame of a state (sweep and monkey). A control counts as drawn when it
is submitted, even if it is scrolled out of view. That is conservative: a row must reach it.

At every press the harness records the keys the press REACHED (`UiPress.Reached`). It never infers them from geometry.
- A plain press reaches what the UI itself routed it to, from the press frame to the release frame:
  - the controls ImGui ACTIVATED (`UiControl.Activated`, `ImGui.IsItemActivated` at record time): hovered in the
    window on top, inside the visible clip, and not disabled;
  - the hit region each painted screen's own `Click` resolved (`ResolvedClick<TKind>`, kept by `AgeScreen`,
    `ActionSurfaceScreen`, `InfoPanel` and `ProgressionScreen` for observation only).
- A Shift press reaches only the inspectable kind it opens, because it inspects and does not click.

A gate row covers what its presses reached (`GateRow.Covers`), and only a passing row counts.

*Review fix (MEASURED by the reviewer and in the tests).* The first version credited every control and region whose
laid-out rect contained the press point. ImGui's item rect is not clipped, so hidden, scrolled-away, covered and
disabled controls counted as pressed. With POLICY open, the action surface is one invisible item about 2,000 px
tall, and a press on `nav:Trends` covered `control:action-surface`. The tests now pin these cases:
- `Coverage_ACommandBarPress_WithPolicyOpen_DoesNotCoverTheActionSurfaceBeneathIt`: at 1280x800 and at the minimum
  window, after one End Turn, a press on `nav:Trends` or `nav:Annals` reaches only that button. The test first checks
  that the old geometric rule would have credited the surface.
- `Coverage_AControlScrolledOutOfItsPanel_IsNotReached`: POLICY is scrolled, and the surface's laid-out rect runs out
  of the panel over other chrome. A press there reaches only the control drawn there.
- `Coverage_APressOnTheActionSurface_ReachesExactlyTheRegionItsClickResolved`: a press on the surface reaches the
  surface and exactly the region its own `Click` answered with. The next press credits nothing of the surface.
- `Coverage_ControlsDisabledUnderTheModalAgeFlow_AreNotReached`: in the "age advance" state, the "flow is modal" row
  presses End Turn and POLICY under the open flow. It passes and covers nothing.

With the stricter rule the gate still passes. Every drawn key in all 9 states is reached by a passing row, and the
allowlist is still empty.

After the sweep and the monkey, each drawn key that no passing row of that state pressed, and that is not on
`UiCoverage.Allowlist` with a reason, is a FAIL row. The allowlist is EMPTY: every drawn key is pressed by a passing
row.

The first run of the check found 18 drawn keys with no row across the states (MEASURED, `--monkey 200`). Rows were
added for them; no allowlist entry was used:
- The pinned card's link, Back, close and "Show in research tree", over the map and over the research screen.
- The research detail panel: SET AS RESEARCH TARGET on an available node selected without ordering it (through its
  card's "Show in research tree"), the panel's inert body, and the narrow window's drawer close.
- The Age panel's research-next line.
- The TURN tab's deficit WHERE rows.
- The grievance contributor rows and both kinds of lever.
- An after-End-Turn pass (area suffix ` (after End Turn)`) for the ANNALS "all entries" toggle, the research-next
  line, and the developer surfaces in the turn-1 states. Those only fill once turns are played; the monkey reached
  them, but the sweep had not.

The check also exposed three info rows that reported "not offered" while the UI did draw that kind: the Age panel's
milestone, its research-next node, and "Show in research tree" from a milestone. The panel scrolls and registers
only what is in view, and the milestones sit below its first screen at 1280x800. These rows now scroll the panel as

**Camera rows: looking changes nothing (IMPLEMENTED).** These rows now also require the world hash and the queued
order list (every `OrderRecord`, in order) to be exactly as before:
- W A S D;
- the map's settlement selection (CameraFocus.CenterOn plus a click);
- a new "centre on a settlement (CameraFocus.CenterOn)" row;
- drag pan, and the three wheel zooms;
- the formation token rows;
- the developer WHERE rows (select and centre).

### 3.5 Eased zoom and pan, the continuous level of detail (M5 workstream P2, 2026-10-11)
