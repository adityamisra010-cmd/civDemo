# M5 PLAYABILITY GATE (M5 hardening, stream H1)

**Status:** the standing playability gate for every playable build from M5 on (Director 2026-10-05 §15: a build is
not "playable" because the test suites pass; it must also pass the manual-interaction-equivalent smoke gate).
Created 2026-10-05 on branch `m5h-h1-ui-playability` (cut from `9bb7423`). This record describes what the gate
does and what it found; the coverage table in §6 is generated by the gate itself (`Sim.Ui --smoke --report`).

Labels as in `docs/m5-playtest-baseline.md`: **MEASURED** (run by the author of this record on this branch),
**IMPLEMENTED** (read in the tree), **INFERRED** (reasoning, not measured).

---

## 1. Why this exists

The playtest build of 2026-10-04 passed Sim.Tests 1460/0/6 and Sim.Ui.Tests 473/473 and aborted on the first click
of Research:

```
imgui_draw.cpp:2261  ImGui::AddDrawListToDrawDataEx
Assertion: draw_list->_VtxCurrentIdx < (1 << 16) && "Too many vertices in ImDrawList using 16-bit indices."
```

None of the 473 UI tests created an ImGui frame. The UI's view models and DrawList painters were tested; the live
path — the ImGui widgets, the DrawList replayed into ImGui's draw lists, `ImGui.Render`, the input routing between
MonoGame and ImGui — was never run outside a window. This gate runs exactly that path.

## 2. The Research-screen crash

**Reproduced (MEASURED).** The canonical founded world (seed 42) at turn 1, the Research screen painted by the
real `ProgressionScreen`, replayed by the real `DrawListImGuiBackend` into a real native ImGui context (ImGui.NET
1.91.6.1's `cimgui`), then `ImGui.Render()`. Without the fix the process aborts with the exact assertion above
(`imgui_draw.cpp:2261`); `Sim.Ui --smoke-control-prefix` reproduces it through the live UI on demand.

**Root cause (IMPLEMENTED, MEASURED).** ImGui indexes vertices with 16-bit indices. A draw list may pass 65,535
vertices only if the renderer declares `ImGuiBackendFlags.RendererHasVtxOffset`; ImGui then opens a new draw
command whose `VtxOffset` rebases the indices, and the renderer adds that offset to each command's base vertex.
The vendored MonoGame renderer (`Sim.Ui/ImGuiIntegration/ImGuiRenderer.cs`) already passed
`baseVertex = vtxOffset + cmd.VtxOffset`, but **nothing ever set the flag**, so every draw list stayed in one
16-bit window. The Research screen is replayed into ONE draw list (ImGui's background list). In the A1 (stone)
era every card carries a pitted-stone texture and freehand outlines, so the A1 Technology tree is large:

| window | A1 Technology tree | vertices in the one draw list (MEASURED) |
|---|---|---|
| 1280×800 (the game's default window) | as it opens | 60,310 |
| 1280×800 | pointer moved over the tree (hover highlight) | up to 68,034 |
| 1280×800 | FIT (whole tree) | 88,362 |
| 1920×1009 (a maximised window) | as it opens | 94,664 |
| 2560×1377 | as it opens | 130,088 |

So in a maximised window the screen crossed 65,535 on the very frame it opened, and in the default window as soon
as the pointer crossed the tree or FIT was pressed. A5/A9 trees stay far below (19,034 / 16,952 at 1280×800).

**Fix (IMPLEMENTED).**
- `ImGuiDrawData.Configure` sets `RendererHasVtxOffset` (called by the renderer's constructor and by the headless
  context) and keeps ImGui's duplicate-ID detector on.
- `ImGuiDrawData.Plan` is the one place a draw call's base vertex (`list start + cmd.VtxOffset`) and start index
  (`list start + cmd.IdxOffset`) are computed; the renderer issues exactly that plan.
- `ImGuiDrawData.Check` validates a rendered frame against the REAL index buffers: the flag is declared, every
  command's indices stay inside its list's index buffer, every index rebased by its `VtxOffset` addresses a vertex
  of the same list, and every list's open 16-bit window is below 65,536.
- `DrawListCull` drops DrawList commands whose conservative bounds miss the target's clip rect (the screen for the
  background list; a window's visible region for a window list), honouring the list's own clip pushes, before
  replay. Its bounds are proven to contain every vertex ImGui emits for each command kind.

The assertion is not suppressed and the screen is not disabled.

**Regression tests (`Sim.Ui.Tests/ResearchScreenRenderTests.cs`, real native ImGui, headless).** Technology and
Civics at A1, A5 and A9, each scrolled from top to bottom at zoom 1, fitted, zoomed fully out and hovered: every
frame passes `Check`. Control: the A1 Technology tree exceeds 65,535 vertices in one list (and opens past it at
1920×1009), and ImGui split it into rebased commands. The draw plan is pinned command by command against the real
index buffers. The cull's bounds contain every emitted vertex per command kind; every command it drops is
replayed alone and shown unable to reach the visible region. Mutants each killed by a semantic test: no flag; plan
without `VtxOffset`; text bound shrunk to 0.4 em per character; clip pushes ignored.

## 3. The gate

**Architecture (IMPLEMENTED).**

| piece | file | role |
|---|---|---|
| `GameUi` | `Sim.Ui/GameUi.cs` | The game's per-frame UI WITHOUT a graphics device: chrome, sections, research and Age screens, action surface, world lens, map interaction, keys. Moved verbatim out of `SimUiGame`. |
| `SimUiGame` | `Sim.Ui/SimUiGame.cs` | A thin MonoGame host: polls input once per Update, draws the terrain bake, rivers and grain on the GPU, calls `GameUi.Update` / `PrepareFrame` / `Draw` between the renderer's BeforeLayout and AfterLayout. |
| `UiControls` | `Sim.Ui/UiControls.cs` | Every ImGui widget records its name, rect and item id each frame. The gate clicks controls where the UI drew them; a repeated item id is a duplicate-ID defect. |
| `ImGuiInput` | `Sim.Ui/ImGuiIntegration/ImGuiInput.cs` | The one MouseState/KeyboardState → ImGui IO translation, used by the renderer and the harness alike. |
| `HeadlessImGui` | `Sim.Ui/Headless/HeadlessImGui.cs` | A real native ImGui context, font atlas built on the CPU, stand-in texture ids, no GPU. |
| `UiFrameHarness` | `Sim.Ui/Headless/UiFrameHarness.cs` | One MonoGame tick per `Frame()`: `GameUi.Update` with scripted input, `ImGui.NewFrame`, `GameUi.Draw`, `ImGui.Render`, then the frame checks (16-bit draw contract, duplicate ids, ImGui's error tooltip). Click = move and hold 3 frames, press, release, one frame for the result. |
| `PlayabilityGate` | `Sim.Ui/Headless/PlayabilityGate.cs` | The states, the per-control script with its expected transitions, and the seeded monkey. |
| `SmokeCommand` | `Sim.Ui/Headless/SmokeCommand.cs` | `Sim.Ui --smoke`: runs the gate, prints the table, exits 0 / 1; routes Windows C-runtime assert dialogs to stderr; a watchdog makes a hang a failure (exit 3). |

**Commands.**

```
Sim.Ui --smoke [--ai-empires N] [--monkey N] [--state NAME]... [--report PATH] [--timeout-minutes M]
Sim.Ui --smoke-control-prefix      # the control: the live UI without RendererHasVtxOffset; must abort
Sim.Ui --frame-cost [--rounds N]   # the Research-screen frame cost table of §2
```

`--ai-empires N` founds every state with N AI empires (by default the states are founded with none, plus one
state with one AI).

**What a check is.** For every interactive control the code draws: click it where it is drawn → no crash → assert
the intended transition (a section opens, a toggle flips, a draft changes, an order is appended to the session's
log, the selection changes, the turn advances, the Age advances, the camera moves …). A control that is not
available in a state must be ABSENT with a stated reason, or visibly locked (a locked research node selects and
its detail panel's button reads LOCKED / KNOWN / CURRENT RESEARCH TARGET / ORDERED; CONFIRM ADVANCE is dim until a
surge is chosen and says so). A control that is drawn but does nothing is a FAIL ("SILENT").

**Every frame** of every check and of the monkey is checked: the draw data's 16-bit contract
(`ImGuiDrawData.Check`), duplicate ImGui item ids among the recorded controls (exhaustive), and ImGui 1.91's own
duplicate-ID warning (`io.ConfigDebugHighlightIdConflicts` is on; its error tooltip window `##Tooltip_Error` is
detected in the draw data — the game draws no tooltips). Both detectors are proven to fire on an injected
duplicate (`PlayabilityGateTests.DuplicateImGuiIds_AreReportedByBothDetectors`).

**The monkey.** A seeded SplitMix64 stream (seed 20261005) chooses, per action: left click (50 %), right click,
drag, wheel ±3, or a key tap from K, Escape, Tab, 1–7, F12, W/A/S/D, arrows, Space (End Turn, at most six per
state), Enter. 400 actions per state by default; an Escape with nothing open is acknowledged (it would exit).

**Out of process.** A native ImGui assertion aborts the process, so the tests run the full gate as a SEPARATE
process (`dotnet Sim.Ui.dll --smoke`) and assert exit 0 and "SMOKE PASSED"; the A1 state and focused scenarios also
run in-process where safe (the capability is declared, so a large list cannot abort).

**Windows.** `.github/workflows/ui-artifact.yml` job `windows-smoke` (windows-latest) downloads the exact win-x64 zip
the `ui-artifact` job published and runs its `app/Sim.Ui.exe --smoke` (the zip's own `cimgui.dll`), failing the
job on a non-zero exit or a missing "SMOKE PASSED"; an informational step runs the control, which must abort. See §8.

**The UI now (IMPLEMENTED, tested).** Clicking a formation token selects it (a selection frame around the token)
and opens a card under the selection card: its name; whose it is and where it is stationed; its family and line
(*Heavy Infantry / Line Infantry: Warband -> Axe warriors -> Bronze-armed infantry*); its current Age form (*Its Age
I form: Warband*); what the next Age does to it (*At the next Age (…): becomes Axe warriors* — the same
`MilitaryQuery.PlanFor` the transition applies); and, in the card's own words: *"Movement and battle arrive with the
Battle Layer (milestone M7). This formation cannot be moved or given orders yet: it stays where it is stationed,
and it modernizes for free when its civilization enters a new Age."* The card's only control is its close
button. Escape, choosing a settlement, or opening the Age panel puts it away. Tests: selection and card content,
no control on the card but close, drags/right-clicks/destination clicks move nothing and write no order, every way
of closing it (`PlayabilityGateTests.Warband_*`).
