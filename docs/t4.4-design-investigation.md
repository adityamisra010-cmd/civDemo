# T4.4 — DYNAMIC SETTLEMENT FOUNDING: ARCHITECTURAL INVESTIGATION AND DESIGN

**DESIGN / INVENTORY ARTIFACT — NOT A RATIFIED DECISION, NOT AN IMPLEMENTATION AUTHORIZATION.**
Investigated against `main` `8586863`. No production code, schema, golden, corridor or frozen
document was changed by this pass. Nothing here is self-certified.

Every rule below is classified **A** explicitly ratified · **B** implied by an existing mechanism ·
**C** natural implementation choice that alters no architecture · **D** genuine director decision.

---

## §0 THE HEADLINE

Three findings shape everything else.

1. **T4.4 is the packet that closes CR-003.** Not a side effect — its stated purpose. CR-003
   §5.2(a): *"how population converts empty land into settled, worked land, and therefore how the
   frontier eventually closes and Malthusian pressure legitimately emerges."* `queue.md`:27: *"the
   corrected constants leave a pre-Malthusian world because nothing fills the frontier, **and the
   Malthus corridors stay quarantined until this exists**."* CR-003 §3 Option 3, the accepted
   ruling: *"the world is now ~1.2 % settled, and a growing population has no way to take the other
   98.8 %."* **(A)**
2. **The architecture is ratified, not open.** D-037 B1: *"Migration currently runs
   settlement-to-settlement, and **ADR-012 rules that with no viable destination people die at
   home. Extend it**: groups may depart into UNCLAIMED land and found new settlements."* T4.4 is an
   extension of migration attached at the ADR-012 hinge. **(A)**
3. **The single largest hazard is ADR-012's own pathology.** A newly founded settlement — small
   population, full catchment, zero deficit — is *structurally identical* to the food-less ruin that
   caused the resurrection cycle. §7.4 addresses it.

## §2 EXISTING SETTLEMENT CREATION (Phase 2)

**There are exactly two paths, and neither is a simulation system.**

| path | when | ids | population | stocks | housing | deposits | polity | catchment |
|---|---|---|---|---|---|---|---|---|
| `WorldFounding.Found` (`WorldFounding.cs:39-40`) | **turn zero only** | loop index, dense from 0 | full culture×religion×class×cohort cross-product; `Ledger.Flow` SOURCE under `InitialEndowment` | one row per good; **grain only** endowed | one row, dwellings endowed | `HinterlandMeans` over a disc | **none** | **none** |
| `CanonicalSchema` deserialization (`:589-594`) | snapshot load | as serialized | — | — | — | — | — | — |

**The load-bearing structural fact: no system in `SystemCatalog.All()` has write access to
`Settlements`.** The table is immutable across the entire simulation — `TurnExecutor` clones it and
nothing ever appends. **T4.4 requires a new table-ownership grant. (B)**

### 2.1 `WorldFounding` decomposed — reusable vs turn-zero

**REUSABLE (pure, safe to call mid-turn):**
- `SettlementSiting.CandidateScores` — documented *"Pure function of its inputs — no state, no
  caches"*; terrain-only, and terrain is static (ADR-008).
- `SettlementSiting.Jitter` / `WorldFounding.U` — SplitMix64 over `(seed, id, slot)`, **no RNG
  stream**.
- `WorldFounding.HinterlandMeans` — *"Deterministic by construction: a fixed row-major scan of a
  fixed disc… No dictionary iteration, no RNG, no LINQ."*
- `LatticeMap.OriginLatticeNode`, `Pathfinder.RelaxCappedFrom`, `TraversalLattice.Build`.

**TURN-ZERO ONLY (must NOT be called mid-turn):**
- `Found` itself — it *constructs* the `WorldState`.
- `ChooseSites` **as written** — takes `count` up front, seeds `spacing[]` to +∞ with **no knowledge
  of existing settlements**, and **throws** rather than returning "no site". Wrong shape for a
  per-turn system.
- Ids as loop index; `new Ledger(world.LedgerFlows)` bypassing `SimContext`; every direct
  `world.X.Add` that reads what it is writing (a Prev-discipline violation).

**BELONGS TO A PIPELINE SYSTEM (must not be duplicated):** `NetworkMeta` (PathBuild — world-scoped,
a second founding must **not** add another row), `Housing` (HousingSystem already materialises a
missing row mid-turn — see §2.2), `Buckets`, `ClassStates`, `Grievances`, `GoodStocks`.

### 2.2 The precedent T4.4 should follow

`HousingSystem.cs:96-101` is **the only existing case of a system materialising a per-settlement row
mid-turn**, and it does so at **zero**:

```csharp
int rowIdx = FindHousing(housing, settlement);
if (rowIdx < 0) { if (pop <= 0) continue;
    rowIdx = housing.Add(new HousingRow(settlement, Conserved.Zero, 0.0, 0.0, 1.0, 0.0)); }
```

**A new settlement therefore starts homeless and builds its own housing. No free dwellings. (B)**

### 2.3 Mandatory state (Phase 7) — what breaks if absent

**Class A — must exist at creation or the settlement is permanently broken:**

| row | failure if missing |
|---|---|
| full `BucketRow` cross-product | `MigrationSystem.cs:322-329` — **no matching destination bucket ⇒ the migrant intent is REFUNDED and nobody can ever arrive.** Also `DemographicsSystem.cs:213` — people stick in a cohort |
| `GoodStockRow` for **every** good | `ProductionSystem.cs:191` *"nothing to credit"* — silently never farms, **forever**; consumption eats nothing; trade cannot move |
| `DepositRow`s | `ProductionSystem.cs:289` *"no endowment → no production (never from nothing)"* — herding and extraction permanently dead, and **unrecoverable**: `Deposits` has no per-turn owner |
| `ClassStateRow` per class | `ClassMobilitySystem.cs:158` — class emergence never fires |
| `GrievanceRow` per class | `NeedsGrievanceSystem.cs:205` — grievance never accrues |

**Class B — emerges by itself, and T4.4 must NOT create it:**
`CatchmentNodeRow`/`CatchmentSummaryRow` (see below), `HousingRow`, `PriceRow`,
`SectorAllocationRow` (falls back to `Sectors.Default`), `PathProgressRow`, and every per-turn
chronicle table.

**A free mechanism, verified verbatim:** `CatchmentSystem.IsStale` opens with
`if (prev.CatchmentSummaries.Count != prev.Settlements.Count) return true;` — **appending a
settlement automatically forces a full catchment recompute on the next turn.** T4.4 writes no
catchment state at all. **(B)**

**And a free field:** `SettlementRow.FoundedTurn` already exists, is written only by
`WorldFounding`, and **no system reads it**. A dynamically founded settlement can record its real
founding turn with **zero schema change**. **(B)**

## §3 MIGRATION TRACED TO ITS ENDPOINT (Phase 3)

```
desired/yr = BaseRatePerYear × CohortProfile[cohort] × PREV count
             × damping(i→j) × viability(j)
             × (gapScale(i→j) × gap(i→j) + FamineFlightFactor × deficit_i)
```

- **damping** `= exp(−travelCost / DampingDecayCostUnits)`; unreachable stores `+∞` so `exp(−∞) = 0`
  — *"zero flow BY CONSTRUCTION, not by branch."*
- **viability** `= max(0, 1 − DestinationDeficitRepulsion × deficit_j)` — ADR-012.
- **overdraw**: desired outflows to ALL destinations computed from Prev; if their sum exceeds the
  bucket's PREV count they are **scaled proportionally**; transfers execute in pinned ascending
  `(source, dest, bucket-key)` order through `MigrationRemainder`.
- **no viable destination** ⇒ `push ≤ 0` for every `dst` ⇒ **no transfer at all**. The system's own
  words: *"there is no exodus without a destination — people die at home instead of circulating
  between ruins."* **This is precisely the hinge D-037 B1 says to extend.**
- Slots **after ClassMobility, before Demographics**. **Stateless. No RNG.**

### 3.1 What would have to happen for migration to become colonization — and the answer

Four architectures were considered against the tree.

| option | verdict |
|---|---|
| **(a) a virtual destination inside migration's pair loop** | **REJECTED.** A frontier site has no `SettlementDistances` row, no deficit and no smoothed attractiveness, so damping, viability and gap would all have to be **synthesised** — three invented quantities inside a director-stabilised equation (T2.8/T2.13). It also puts site selection inside a hot O(n²) loop |
| **(b) a separate system AFTER migration, drawing from LIVE post-migration buckets** | **CHOSEN** |
| **(c) a new branch of migration** | **REJECTED** — same synthesis problem as (a), and it would put `Settlements` write access into the system the stabilization ruling governs |
| **(d) anything else** | no tree support |

**Why (b) is correct and safe.** Migration's overdraw scaler already caps total outflow at the
bucket's **PREV** count. A later system that also read PREV would **double-spend**. Reading the
**live, post-migration** bucket counts cannot: whoever migration already moved is gone, and
`ClampToAvailable` backstops the floor. Founding therefore takes only from those migration left
behind — which is exactly D-037 B1's population, *the people with nowhere viable to go.* **(C)**

## §4 SITE SELECTION (Phase 4)

`ChooseSites` already does everything needed **except** account for existing settlements:

- builds its own lattice via `TraversalLattice.Build(terrain, riverCostFactor)` — **already
  river-aware, so T4.7 is honoured by reuse and would be bypassed only by writing a second
  algorithm** *(this is the strongest argument against inventing one)*;
- `CandidateScores` + a score-floor percentile;
- spacing enforced as **travel cost**, `minSpacingCostUnits = CostUnitsForIdealGroundKm(lattice,
  MinSpacingKm)`, relaxed after each pick by a capped Dijkstra `RelaxCappedFrom` — *"no network
  overlay — spacing is a worldgen property of raw terrain"*;
- argmax by strictly-greater on an ascending scan = **(score DESC, id ASC)**, the constitution's
  composite key.

**The only change needed is how `spacing[]` is initialised.** At turn zero it starts `+∞`
everywhere; mid-turn it must be **pre-relaxed from every existing settlement's site cell** before
the argmax. That is the same machinery with a different seed — **not a second site-selection
algorithm**. **(C)**

**Cost.** `CandidateScores` and the lattice are pure functions of static terrain (ADR-008), so both
are constant for the whole game and must be computed **once and cached**, never per turn.
`CatchmentSystem` already sets the precedent of building the lattice inside a system and recomputing
only on a staleness signal.

**Lattice participation.** A settlement founded at turn *t* gets its catchment at *t+1* via the
count-mismatch staleness, and its `SettlementDistances` row on the same rebuild. Until then
`MigrationSystem` reads `arableKm2 = 0.0` by default and `damping = 0` for the missing pair — it is
**invisible to migration for exactly one turn, by construction**, which is the correct Prev
discipline rather than a defect. **(B)**

## §5 "UNCLAIMED LAND" (Phase 5)

### 5.1 Territory is keyed to SETTLEMENTS, not to land

```csharp
public record struct ClaimRow  (PolityId Polity, SettlementId Place, double Strength);
public record struct ControlRow(PolityId Polity, SettlementId Place, double Strength);
```

Both are `(Polity, **SettlementId**, Strength)`. **There is no representation of political territory
over land, cells, regions or area anywhere in the tree.** Both tables are still **schema-only** at
`8586863` — the sole `.Add` outside tests is snapshot deserialization, and the sole non-test reader
is `AppropriationSystem`, which reads for *absence*. There is no `Polities` table at all.

### 5.2 "Unclaimed" is NEVER DEFINED — the tree carries two unreconciled senses

Every occurrence was enumerated. The tree uses the word in two different ways and never reconciles
them:

| sense | where | keys on | usable today? |
|---|---|---|---|
| **political** — no polity asserts a right | D-037 B1, m4-spec:265 | `ClaimRow` | **vacuous** — `Claims` is empty in every live world, so *all* land is "unclaimed" |
| **economic/land** — no settlement works this ground | `queue.md`:17 (*"large, fertile, reachable, unclaimed hinterland"*), `cr-003.md`:241 | `Pathfinder.Partition.Owner` / `CatchmentNodeRow` | **yes — this is the operative sense** |

`Pathfinder.Partition` assigns every lattice node an `Owner` = settlement by the composite key
`(travel cost, settlement index)`, with `−1` commented *"unclaimed"* — and its doc explicitly
disclaims the political reading: *"M3 has no polity borders (walls are D-037's business, not the
hinterland's)."* Its persisted form is `CatchmentNodeRow(Settlement, LatticeNode, TravelCost)`.

### 5.3 THE RATIFIED SENTENCE THAT SETTLES IT — D-041 E2

`docs/d041-attachment.md:113-118`, verbatim:

> **E2. DOES NOT AFFECT SETTLEMENT SPACING.** … **attachment constrains where a polity can HOLD a
> settlement, not where one can be PLACED.** … **The constraint on placement is LAND** — two
> settlements sharing one catchment — **and it belongs to colonization's own model**, which is what a
> future removal of `minSpacingKm` waits on. **ADR-018 keeps the spacing floor until then.**

**This is explicitly ratified (A) and it is the most consequential sentence for T4.4's design.** It
says three things:
1. the placement constraint is **LAND — two settlements sharing one catchment**, not a distance;
2. **that model is colonization's own to build** — i.e. T4.4 owes it;
3. **`minSpacingKm` is an interim stand-in** that ADR-018 keeps *until* T4.4 supplies the real one.

**Correction to an earlier reading in this document:** I first concluded that travel-cost spacing was
the *only* expressible notion of "taken land". That was wrong. `CatchmentNodeRow` is a persisted,
per-node, settlement-keyed partition, and D-041 E2 names catchment overlap as the intended
constraint. Spacing is the placeholder; catchment overlap is the target. See **DECISION 3**.

### 5.4 The four sub-questions

1. **How can the simulation determine a site is available?** There is **no occupancy representation
   at all** — no cell→settlement reverse index, no `SiteCell` uniqueness invariant, no availability
   predicate. Two settlements sharing a `SiteCell` is **not prevented**; distinctness today is an
   *incidental* by-product of `minSpacingKm = 95.2` plus a strict `<` in the spacing test. Note also
   the granularity mismatch: spacing is evaluated on the **origin lattice node** (stride 4, ~16 km),
   while sites are ~4 km cells, so two different cells inside one node read the same spacing value.
   **(C — not addressed; T4.4 must supply it)**
2. **What does "unclaimed" mean?** Undefined in the documents; the operative sense is the
   **economic/catchment** one, and D-041 E2 ratifies land/catchment overlap as the placement
   constraint. **T4.4 must NOT invent a political territorial representation** — D-037's model is
   settlement-keyed and its mechanisms are later packets. **(B + A)**
3. **Can founding legally create a stateless settlement?** **Yes, and today it cannot do otherwise.**
   D-037 A3: control is *"exactly one, or none (stateless)"*; B1: *"refugee foundings may be
   stateless."* Nothing writes `ControlRow`, so every settlement is already stateless — which is why
   `AppropriationSystem.IsStateless` works. **Two caveats T4.4 inherits:** statelessness is currently
   *universal* and therefore not a discriminator (T4.5 learned this the hard way — raiding on
   statelessness alone made every village raid); and the one-or-none cardinality is **documented but
   unenforced**, so **T4.4 would be the first packet capable of violating it.** **(A + B)**
4. **Does a new settlement inherit the founder's allegiance?** **Automatic inheritance is ruled out
   as an axiom** — B1's *"NEED NOT belong to the polity they left"*, reinforced by A2: *"A POLITY IS
   A CLAIM, NOT A CONTAINER… ownership is a contingent, simulated quantity."* But note **D-037 C1
   lists *"settlement founding (a polity's own colonists)"* as a legitimate CLAIM source** — so a
   polity founding may generate a `ClaimRow` even while `ControlRow` stays absent. **At M4 the
   question is moot in practice** (no `Polities` table; `BucketRow`'s key carries no polity, so a
   migrating population has no affiliation to inherit), but the *rule* is already ratified for when
   it is not. **(A for "not automatic"; C for the positive rule)**

## §7 THE DESIGN

### 7.1 Shape
A new system, **`ColonizationSystem`**, owning `Settlements` (a new grant) plus the tables a new
settlement's mandatory rows live in. It runs **after `migration`, before `demographics`**.

### 7.2 Per turn, settlement-major ascending (law 5)
1. Read the source's **live** post-migration population and its PREV land pressure.
2. If the source is not under enough pressure to colonise, skip (DECISION 1).
3. Select a site: cached `CandidateScores`, `spacing[]` pre-relaxed from every existing settlement,
   argmax by **(score DESC, cell id ASC)**. No site ⇒ no founding (never throw).
4. Allocate the next settlement id as `max(existing id) + 1` — dense, ascending, deterministic.
5. Create the **Class A** rows: full bucket cross-product at zero, every `GoodStockRow` at zero,
   `DepositRow`s from `HinterlandMeans`, `ClassStateRow`s, `GrievanceRow`s.
6. **`Ledger.Transfer`** the founding party out of the source's buckets into the matching new
   buckets, key for key.
7. **`Ledger.Transfer`** provisions (grain) from the source's store into the new store — the
   colonists carry food; nothing is minted.
8. Write `SettlementRow(newId, siteCell, FoundedTurn: currentTurn)`.
9. Seed `SmoothedAttractivenessRow` — see §7.4.

Housing and catchment are deliberately **not** created; they arrive by the existing mechanisms.

### 7.3 Clearing cost
The spec names it. The **minimal tree-native form is the provisions the colonists carry** (step 7):
they must eat until their first harvest, and that grain is *transferred*, not created. That is a
real cost to the source, needs no new mechanism, and cannot mint. A richer land-clearance mechanism
(arable expanding as labour is invested) is a materially larger system — see DECISION 2.

### 7.4 THE ADR-012 HAZARD — the most important design element

A new settlement has a small population and a full catchment, so its instantaneous per-capita
attractiveness `A = R/P` is **enormous**. This is *exactly* the food-less-ruin profile that produced
ADR-012's resurrection cycle (*"1,520 arrivals against 884 same-turn deaths in one turn"*). Worse,
the EMA does not damp it: migration's own contract says **"a settlement's first sighting initializes
S = A (the filter starts converged)"** — so a new settlement would arrive pre-converged on its own
inflated signal and become an instant world magnet.

**Mitigation, using only existing architecture:** seed the new settlement's
`SmoothedAttractivenessRow` with **the founding source's current smoothed value**, not with its own
instantaneous `A`. The founders' expectation of the world is the source they left. This introduces
no constant, matches the D-020 warm-up-guard pattern already used for emergence, and lets the EMA
converge to the true value over its normal window instead of in one turn. **(C)**

## §8 PIPELINE POSITION (Phase 8)

```
catchment · harvestweather · production · appropriation · consumption · price · trade
· housing · classmobility · migration · **colonization** · demographics · needsgrievance · pathbuild
```

**Why here, from dependencies rather than intuition:**
- **After `migration`** — the only position where drawing from live buckets cannot double-spend
  against migration's PREV-based overdraw scaler (§3.1).
- **Before `demographics`** — the founding party is ordinary people and should age and breed this
  turn like everyone else.
- Production/consumption/housing have **already run**, so the new settlement produces nothing in its
  founding turn. That is correct: it was founded mid-year.
- Catchment is slot 1, so the new settlement's catchment is computed **first thing next turn** by the
  count-mismatch staleness — no partial visibility.

**The invariant** — *a settlement must never be partially visible to systems that expect its state
to exist* — is satisfied because every **Class A** row is created **atomically in step 5 before the
population transfer**, and because migration sized its arrays from `prev.Settlements` and therefore
cannot see the new settlement at all this turn.

## §9 ANTI-SPAM AND FOUNDING RATE (Phase 9)

**The ratified purpose argues against a hard limiter.** CR-003's accepted ruling is that the world
is *"~1.2 % settled"* and population *"has no way to take the other 98.8 %."* A counter that caps
foundings per turn would throttle the exact behaviour the packet exists to create.

**What bounds founding emergently, all already in the tree:**

| bound | mechanism | strength |
|---|---|---|
| **candidate exhaustion** | every founding removes a `minSpacingKm` travel-cost disc (or, under DECISION 3, a catchment) from the candidate pool | **strong — and self-closing, which IS "the frontier closes"** |
| score floor | `ScoreFloorPercentile` makes poor land ineligible | strong |
| available population | the party is a `Transfer` out of live buckets, `ClampToAvailable` | strong |
| travel cost | distant frontier is expensive to reach | moderate |
| land pressure | a comfortable settlement has no reason to colonise (DECISION 1) | **the primary regulator** |

**Assessment: the spacing mechanism alone is a genuine, self-tightening bound** — the candidate set
shrinks monotonically and the frontier provably closes, which is the ratified goal. A per-turn
counter is therefore **not architecturally necessary**, and adding one would be a free-floating
modifier (law 2) on a mechanism that already saturates — the identical argument migration used to
DECLINE a crowding-saturation term.

The remaining question is only the **rate** at which the frontier fills, which is governed by the
pressure threshold, not by a counter. **Distinguish carefully:** per-settlement founding (one party
per source per turn is the natural shape), global founding (bounded by candidate exhaustion),
per-civ founding (**meaningless at M4 — no settlement belongs to a polity**).

| concern | resolution | class |
|---|---|---|

## §12 ADVERSARIAL REVIEW OF THE DESIGN (Phase 12)

| # | proposition | verdict under this design |
|---|---|---|
| 1 | cannot create population from nothing | **HOLDS** — `Ledger.Transfer` only; `InitialEndowment` forbidden after turn 0 |
| 2 | cannot create goods from nothing | **HOLDS** — provisions are transferred |
| 3 | source loses exactly what moves | **HOLDS** — `Transfer` is one operation |
| 4 | cannot occupy an illegal/occupied site | **HOLDS ONLY IF T4.4 ADDS THE GUARD.** Nothing in the tree prevents two settlements sharing a `SiteCell`; distinctness today is *incidental* to `minSpacingKm = 95.2` plus a strict `<`. Spacing is also evaluated at ~16 km lattice-node granularity while sites are ~4 km cells. **T4.4 must assert site distinctness explicitly rather than inherit it** |

## §14 THE TWO GENUINE DIRECTOR DECISIONS

### DECISION 1 — the founding trigger and party size

**Question.** What land pressure justifies sending colonists, and how large is the founding party?

**What the tree says.** T4.2 made land pressure real and is T4.4's declared dependency (*"land
pressure needs scarcity"*). T4.1 Q1 measured the bind ratio: land = `km²·yr⁻¹ × 26.0` vs labour =
`adults × 5.0 × toolFactor`, both food-units/yr into one `min()` — **so a settlement whose land term
binds is exactly a settlement under land pressure, and it is already computed.** The attractiveness
term `LandWeight × arableKm2 / P` is a per-capita land measure that already exists.

**What it does not say.** No threshold, and no minimum founder population, exists anywhere. The
world's founding cohort sizes (~350–500 jittered) are the only comparable magnitude.

**Option A — derive both from existing quantities.** Trigger on the bind ratio crossing into
land-binding; size the party so the *new* settlement's per-capita land is no more attractive than
the source's (which also directly damps the §7.4 hazard). Adds **no new constant**.
**Option B — a derived TUNE pair** (`colonizationPressureThreshold`, `minFounderParty`) with a
reference class stated before the number, as `tauYears` (40, band 25–60) and `riverCostFactor` (0.20,
band 0.10–0.20) did.

**Recommendation: A, falling back to B only where A leaves a quantity genuinely undetermined.** A is
self-regulating and needs no calibration; B risks becoming the fitted constant CR-002/CR-003 forbade.

**Consequence.** A: founding rate is emergent and frontier closure is self-timing, but harder to
steer. B: directly tunable, but every value must be derived and defended, and a wrong threshold
either freezes the frontier or floods it.

### DECISION 2 — is "clearing cost" provisions, or a land-clearance mechanism?

**Question.** m4-spec names *"clearing cost"*. Is it satisfied by colonists carrying provisions
(§7.3), or does T4.4 owe a mechanism where worked land expands as labour is invested?

**What the tree says.** CR-003 calls it *"how population converts empty land into settled, **worked**
land"* — which reads like the larger mechanism. But arable is currently computed from **terrain via
the catchment**, not from any cleared-land stock, so "worked land" has no carrier today.

**What it does not say.** Nothing specifies a clearing rate, a cleared-land stock, or how it would
interact with `EffectiveArableKm2`.

**Option A — provisions only.** Founding costs the source real grain and population; arable stays
terrain-derived. Small, conserved, no new state.
**Option B — a land-clearance stock.** A per-settlement cleared-arable quantity that grows with
labour and gates production. Materially larger: new conserved-ish state, a new rate constant, and it
changes what `EffectiveArableKm2` means — touching the density corridor and CR-002's denominator.

**Recommendation: A for T4.4, with B recorded as a separate follow-up packet.** A delivers frontier
closure — CR-003's actual requirement — at a fraction of the blast radius. B rewrites the arable
denominator that two quarantined corridors are measured against, and should not ride along inside a
packet that is already the one closing CR-003.

**Consequence.** A: frontier fills, Malthusian pressure can emerge, corridors become measurable
again, and clearing is a real but simple cost. B: richer economics, but it lands a new denominator
under `densityPerArableKm2` while that corridor is still quarantined — two moving parts under one
measurement.

## §15 WHAT IS RESOLVED WITHOUT THE DIRECTOR

Everything in §§2–13, and **three questions that looked like director decisions and are not**:

- **whether a new settlement inherits allegiance** — moot at M4 (no `Polities` table, no polity on
  the bucket key), and the rule is already ratified: B1's *"NEED NOT"* forbids automatic inheritance
  as an axiom, while D-037 C1 keeps founding as a legitimate *claim* source for when polities exist;
- **whether to add a founding rate limiter** — no: candidate exhaustion is a genuine self-tightening
  bound, and a counter would be a law-2 free-floating modifier on a mechanism that already
  saturates, which is the identical argument migration used to DECLINE a crowding term;
- **which architecture founding takes** — ratified by D-037 B1 plus migration's overdraw discipline;
  the three alternatives fail on synthesised quantities or double-spend (§3.1).

**One question turned out to be a real decision only after the tree was read properly:** what
"unclaimed" means. My first pass concluded spacing was the only expressible notion. D-041 E2 says
otherwise — the constraint is catchment overlap, the model belongs to this packet, and `minSpacingKm`
is the interim floor. That is **DECISION 3**, and it exists because the ratified text asks T4.4 for
something the first reading missed.

**THE THREE DECISIONS ARE INDEPENDENT AND CAN BE ANSWERED SEPARATELY.** Everything downstream of each
is already resolved above: DECISION 1 gates only the trigger arithmetic in §7.2 step 2 and the party
size in step 6; DECISION 2 gates only §7.3; DECISION 3 gates only the legality predicate in §7.2
step 3. The rest of the design — pipeline position, the Class A row set, the transfer discipline, the
EMA seeding, determinism, measurements and the adversarial plan — stands regardless of how all three
are answered.

### DECISION 3 — does T4.4 replace `minSpacingKm` with the catchment-overlap placement model?

**Question.** D-041 E2 ratifies that the placement constraint is **LAND — two settlements sharing one
catchment** — assigns that model to **colonization's own packet**, and says `minSpacingKm` is what a
*"future removal"* waits on, with **ADR-018 keeping the spacing floor until then**. T4.4 is that
packet. Does it build the catchment-overlap model now, or ship on the spacing floor and leave the
replacement to a later packet?

**What the tree says.** E2 is explicit that the real constraint is catchment overlap and that it
belongs here. The carrier already exists and is persisted: `CatchmentNodeRow(Settlement, LatticeNode,
TravelCost)`, produced by `Pathfinder.Partition`, whose `Owner = −1` is literally commented
*"unclaimed"*. So the data needed to ask *"would this site's catchment overlap an existing one?"* is
already computed every time the catchment is rebuilt.

**What it does not say.** How much overlap is permissible, or whether overlap should forbid a site
outright or merely penalise its score. Nothing quantifies it anywhere.

**Option A — ship on the spacing floor (ADR-018 unchanged).** T4.4 reuses `minSpacingKm` exactly as
worldgen does. Smallest blast radius; the spacing machinery is already river-aware and already
deterministic. Leaves E2's model unbuilt and the floor in place.
**Option B — build the catchment-overlap model in T4.4.** Placement legality becomes "this site's
catchment does not overlap an existing settlement's beyond X". Discharges E2 as written and lets
ADR-018's floor eventually retire.

**Recommendation: A for T4.4's first implementation, with B as the immediate follow-on** — and the
reason is measurement, not effort. T4.4 is already the packet closing CR-003, so it will move all
three behavioural goldens and is the first mechanism able to make the Malthus corridors measurable
again. Changing the *placement rule* in the same packet would put a second moving part under
`densityPerArableKm2` — a corridor that is **still quarantined** and whose denominator is exactly
catchment-derived arable. Ship frontier closure first, measure it, then retire the floor against a
known baseline.

**Consequence.** A: E2 remains owed, and `minSpacingKm` keeps enforcing a 16 km-granular,
distance-shaped proxy for a land-shaped constraint — settlements may still be spaced by travel cost
rather than by whether their fields collide. B: the ratified model lands sooner, but it changes what
counts as a legal site *while* the corridor that measures land use is quarantined, and the two
effects would be hard to separate afterwards.
